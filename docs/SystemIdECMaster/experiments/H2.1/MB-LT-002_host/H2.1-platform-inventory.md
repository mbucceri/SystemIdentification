## Important platform risks

These are risks or evidence gaps, not architecture decisions:

- The running kernel is a stock Ubuntu generic kernel configured for voluntary
  preemption, not a configuration identified as PREEMPT_RT.
- The relevant physical Ethernet interface was `DOWN` and reported
  `NO-CARRIER` during collection.
- The available NIC is an Intel I219-LM using `e1000e`; no conclusion is made
  here about native EtherCAT support or driver suitability.
- The probe process has a realtime priority limit of zero. Whether the
  eventual test process receives controlled realtime scheduling limits is
  unresolved.
- `cyclictest`, `perf`, `trace-cmd`, and `ethtool` are unavailable, reducing
  immediate diagnostic and timing-tool coverage.
- The frequency governor is `powersave`, and CPU frequency is dynamic under
  `intel_pstate`; its effect must be measured rather than assumed.
- The machine is also running desktop, Docker, Wi-Fi, graphics, and other
  services/modules. Their effect on timing must be evaluated under defined
  representative load.
- The exact target probe output-directory argument and whether the command was
  started from a copied probe directory or repository checkout were not
  recorded in the raw evidence.

## Required follow-up experiments and questions

1. Confirm the intended EtherCAT physical port and establish link state with a
   safe, explicitly authorized setup. Record the interface name and endpoint
   without changing host configuration as part of the inventory.
2. Resolve the H2.2 IgH/EtherLab baseline question: availability, source,
   build prerequisites, kernel-module requirements, userspace library, and
   native/generic NIC options. This report does not select among them.
3. Run H2.3 stock-kernel measurements first, including scheduler behavior,
   CPU affinity, IRQ behavior, memory locking, and frequency state. Any host
   changes require a separate bounded experiment and rollback procedure.
4. Run H2.4’s independent 1 ms periodic timing experiment on MB-LT-002 under
   documented idle and representative-load conditions. Measure period error,
   wake-up jitter, execution time, and violations against the ±100 µs target.
5. Provide timing/trace tools only through an explicitly authorized target-host
   preparation step; their absence here is recorded, not silently corrected.
6. Determine whether the target process can obtain the required scheduling and
   memory-locking limits through the existing operational procedure. Do not
   infer this from the probe shell limits.
7. Clarify OQ-003: period error versus wake-up/cycle-start jitter, violation
   counting, and response policy.

## Limitations and non-conclusions

This inventory alone does not verify:

- a 1 ms cyclic period;
- the ±100 µs timing tolerance;
- PREEMPT_RT suitability or necessity;
- NIC or `e1000e` suitability for EtherCAT;
- EtherCAT frame exchange, slave state, or Working Counter behavior;
- target suitability for physical robot operation.

No architecture decision, IgH release selection, kernel strategy, NIC/driver
strategy, or scheduler strategy is made here.
